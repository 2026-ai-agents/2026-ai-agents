# 강의 문서 세션 분할 계획

`docs/course-plan.md`의 절 하나를 강의 문서 하나로 옮겨, 일차 단위가 아니라
**세션 단위 URL**을 갖게 하는 작업의 계획서다. 실행 전 합의용 문서이며,
작업이 끝나면 결과를 `site/README.md`와 `CHANGELOG.md`에 반영한다.

## 왜 바꾸는가

지금은 일차 하나가 문서 하나다.

```plaintext
/course/day-01/      Day 1 전체 (240분, 8개 블록)
```

세션마다 다루는 저장소·릴리즈·예제가 다르므로 한 문서에 다 넣으면 길어지고,
수업 중 "지금 보는 자료" 링크를 세션 단위로 줄 수 없다. 바꾼 뒤에는 이렇게 된다.

```plaintext
/course/day-01/                  Day 1 개요 (로드맵·릴리즈 사다리·세션 목록)
/course/day-01-session-01/       오리엔테이션과 환경 점검 (15분)
/course/day-01-session-04/       Tool calling 심화 (40분) → v0.2
```

## 슬러그 규칙

- 파일: `site/src/content/courses/ko/day-<NN>-session-<NN>.mdx`
- URL: `/course/day-<NN>-session-<NN>/`
- 개요 문서는 기존대로 `day-<NN>.mdx` → `/course/day-<NN>/`
- 두 자리 zero-padding을 지킨다. `day-1-session-1` 같은 변형을 만들지 않는다.

### order는 내림차순이다 (중요)

테마의 `getCourses()`는 `order`를 **내림차순**으로 정렬한다. 구현은
`stack-site-builder/src/lib/courses.ts`에 있고, 큰 값이 먼저 나온다. 그래서
시간 순서대로 보이게 하려면 뒤 세션일수록 작은 값을 줘야 한다.

```plaintext
order = (4 - 일차) * 1000 + (900 - 세션번호)      # 개요는 세션번호 0
```

| 문서 | order |
| --- | --- |
| `day-01` (개요) | `"3900"` |
| `day-01-session-01` … `-08` | `"3899"` … `"3892"` |
| `day-02` (개요) | `"2900"` |
| `day-02-session-01` … `-05` | `"2899"` … `"2895"` |
| `day-03` (개요) | `"1900"` |
| `day-03-session-01` … `-06` | `"1899"` … `"1894"` |

- 실제 빌드로 확인한 동작이다. `3899` → `3898` → `3897` 순서로 표시된다.
- **기존 `day-01`/`day-02`/`day-03`의 `order`가 `"01"`/`"02"`/`"03"`으로
  들어가 있는데 방향이 반대다.** 지금은 `/course/`가 카테고리로 먼저 묶여서
  결과가 우연히 맞을 뿐이고, 한 카테고리에 문서가 둘 이상 생기는 순간 드러난다.
  이 작업에서 위 표대로 교체한다.

### hours는 비워 둔다

테마에 `hours` 필드가 있고 카드와 상세 페이지 양쪽에 그대로 표시되는 것을
확인했지만, **쓰지 않는다**. 세션 시간은 사이트 어디에도 표기하지 않는다.
자세한 이유는 아래 결정 사항 참고

## 개요 문서의 역할

개요 문서(`day-01` 등)는 세션 문서로 옮겨간 내용을 중복하지 않고, 일차 전체를
조망하는 것만 남긴다.

- 그날의 교재 저장소와 형태
- 릴리즈 사다리 표 (세션과의 대응)
- 세션 목록 표: 제목과 링크만 두고 시간은 넣지 않는다
- 그날의 큰 그림 mermaid, 실패 재현 시나리오 요약

## 슬라이드

덱도 세션과 1:1로 간다. 폴더명을 강의 슬러그와 같게 두면 대응이 자명하다.

```plaintext
site/src/content/slides/ko/day-01-session-04/index.mdx
```

- 강의 문서의 `slides: ["day-01-session-04"]`로 연결한다
- 지금 있는 `slides/ko/day-01/`은 내용이 오리엔테이션(과정 규칙·저장소·릴리즈
  사다리·Day 1 흐름)이므로 **`day-01-session-01`로 옮긴다**
- 덱이 필요 없는 세션은 `slides: []`로 두고 나중에 채운다

## 결정 사항

원안 점검 뒤 내린 결정이다. `course-plan.md`는 외부 원본이라 고치지 않으므로,
사이트 콘텐츠가 원안과 갈리는 지점을 여기에 남긴다.

### `core` 저장소는 채택하지 않는다 (2026-08-14)

원안 §2.1·§9의 `core`(LiteLLM 래퍼 + budget guard 공용 라이브러리)를 두지
않는다. 저장소는 8개가 된다.

- 원안 어느 세션에도 `core`를 소개하는 지점이 없다. 가르치지 않는 저장소가 남는다
- Day 1의 2절(LiteLLM)과 6절(하네스)이 정확히 그 두 가지를 해부하는 세션이다.
  같은 것을 감싼 라이브러리를 따로 두면 원리를 직접 본다는 Day 1의 목적과 어긋난다
- §2.1은 "각 저장소는 완전히 독립된 compose 스택", "공통인 것은 시작 명령뿐"이라고
  못박는다. `core`는 8개 저장소가 공유하는 유일한 결합점이 되어 이 원칙의 예외가 된다
- 릴리즈 사다리의 약속과 충돌한다. `git checkout v0.2` 후 `compose up`이 그 시점의
  동작을 재현하려면, 그 태그가 `core`의 어느 버전과 맞는지까지 고정해야 한다
- 수업 중 실습·과제가 없으므로 학생이 `core`를 직접 설치해 쓸 일이 없다

**대가**: budget guard와 LiteLLM 래퍼 코드가 저장소마다 중복된다. 이는 의도된
중복이다. 저장소 하나를 클론해 그것만으로 재현되는 쪽이 중복 제거보다 중요하다.

반영 완료: 루트 `README.md` 저장소 표, `about.mdx` 저장소 표와 "수료 시 얻는 것",
`stacks/ko/litellm.mdx`

### 세션 시간은 사이트에 표기하지 않는다 (2026-08-14)

세션 시간은 사이트에 표기하지 않는다. `hours` 프론트매터도, 일차 개요의 세션
목록 표도 비운다.

- 휴식 시간을 따로 배치하지 않는다. 진행하다 시간이 남거나 모자라면 그 자리에서
  단원을 건너뛰며 조절한다. 강사가 현장에서 판단할 몫이다
- 그래서 분 단위를 사이트에 박아 두면 지키지 못할 약속이 된다. 수강생이 보는
  자료에는 순서만 있으면 된다
- 원안의 세션별 시간은 이 문서의 세션 목록 표에 참조용으로 남겨 둔다.
  나중에 시간을 노출하기로 하면 `hours`를 채우면 된다

### Day 1 랩 저장소 이름은 `day-01` (2026-08-14)

원안의 `day1-agent-lab` 대신 실제 저장소 이름을 `day-01`로 확정했다.
일차와 저장소가 1:1이 되어 강의 슬러그(`day-01-session-NN`)와 저장소 이름이
정렬된다. 사이트의 모든 참조(클론 URL·저장소 표·규칙 예시)를 `day-01`로
맞췄고, 원안(`course-plan.md`)만 원문 그대로 남는다.

### ★ 구분은 표기하지 않는다 (2026-08-14)

처음에는 원안의 파일별 별표(합계 20종)를 세션 문서에 옮겼으나, 예제 51종을
전부 수업에서 실행하기로 하면서 ★ 구분 자체를 걷어냈다. 이로써 원안 점검의
★ 개수 불일치(§8 "약 25종" vs 실제 별표 20개) 문제도 사이트 쪽에서는
소멸한다. 원안을 갱신할 때 §8의 별표 서술을 함께 정리하면 된다.

### booking-agent는 두 입장으로 확장한다 (2026-08-15)

원안 §6.2(레스토랑 예약, app·ui·db 3컨테이너)를 **손님/사장 두 입장**으로
확장했다. 컨테이너는 4개(app·ui·admin·db)가 된다.

- 손님(ui, :8501): 이름+전화의 가벼운 로그인, 대화 예약, 확인 카드(interrupt),
  조회·취소
- 사장(admin, :8502): 비밀번호 로그인, 승인/거절 대시보드, 운영 상담
  에이전트(고정 도구 + 읽기 전용 run_sql 도구)
- 원안의 "확정 직전 interrupt"는 손님의 최종 확인(human-in-the-loop)으로
  유지하고, **사장의 승인은 도메인 상태 머신**(requested → confirmed/declined)
  으로 분리했다. 두 "승인"의 구분 자체가 수업거리다
- run_sql(LLM이 SELECT 작성)은 원안에 없는 추가다. 고정 도구 vs 자유 쿼리라는
  도구 설계 스펙트럼과 세 겹 방어(SELECT 한 문장·자동 LIMIT·READ ONLY)를
  가르친다
- 한때 meeting-room-agent(Track A)에서 겹침 판정 등을 차용하는 안을 검토했으나
  철회했다. booking-agent의 코드는 전부 새로 썼다

### secretary-agent 세부 결정 (2026-08-15)

원안 §6.3의 뼈대는 그대로 두고 다음을 정했다.

- db 이미지는 `pgvector/pgvector:pg17`. v1.0 의미 검색이 LangGraph
  PostgresStore의 벡터 인덱스를 쓴다. 임베딩은 `gemini/gemini-embedding-001`
  768차원, 문자열은 `agent/config.py`에만
- 일정 도구(add_event·my_events)를 최소로 곁들인다. 비서가 할 일이 있어야
  기억이 살아나고, 도메인 행(thread 무관)과 대화 기억(thread 안)의 수명
  대조가 v0.1의 사고 재현이 된다
- interrupt는 재사용하지 않는다. 앞 세션에서 배운 개념이라 이 세션의
  예산은 기억에 쓴다 (교안에 생략 이유 명시)
- thread는 사용자마다 하나가 아니라 대화마다 하나. "새 대화" 버튼이
  세션의 주인공이다
- booking의 편의 규약(전화 정규화, named volume, 새로고침 복원, HTTP 경유
  데모)을 처음부터 반영
- 테스트의 임베딩은 결정적 해시 대역(키 없이 통과), 의미 순위 품질은
  데모에서 실측

### 확인 필요

- **음식 DB 건수**: `food-rag-agent` 작업 시점으로 미뤘다. 위 결정 사항 참고
- **권장 RAM**: §10은 8GB 이상 권장이다. `food-rag-agent`는 컨테이너가 4개이고
  (app·ui·db·rag) `coding-agent`는 산출물 스택이 따로 뜬다. 16GB 권장이 안전하다.

### 이상 없음

- Day 2 4개 · Day 3 3개, 제품형 에이전트 7종 집계가 §2.1·§8·§9에서 일치
- 릴리즈 단수 표기(5단·4단)가 실제 나열과 전부 일치
- 예제 51종이 6개 폴더 합계와 정확히 일치 (11+10+10+4+6+10)
- 실패 재현 시나리오 5종이 §2.2와 §8에서 일치
- MCP를 Day 1(가져오기)과 Day 3(내어주기)으로 나눈 구성이 일관됨
- 총 시간 720분이 240분 × 3일과 일치
