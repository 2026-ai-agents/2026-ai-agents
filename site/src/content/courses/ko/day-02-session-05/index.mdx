검색(pgvector)이 여기서는 **전용 벡터 저장소**로 승격됩니다.

| 데이터 | 출처 | 라이선스 |

| 위키 설명 1081건 (docs) | 한국어 위키백과 "한국 요리" 분류 수집 | CC BY-SA 4.0, 행마다 원문 URL |

#### 19,495행에서 1000건을 고른 기준

큐레이션 원칙은 저장소의 `scripts/`에 재현 기록으로 남아 있습니다.
프랜차이즈 브랜드 메뉴 15,225행을 제외하고, 같은 음식의 여러
기원(가정식·외식·급식)에서 하나를 고르고, 위키와 이름이 매칭되는 음식
155건을 전부 넣은 뒤 23개 분류에서 고르게 채웠습니다. **1000건 중
845건은 위키 문서가 없습니다**. 현실 데이터의 결측을 감추지 않고,
매칭된 것만 근거 발췌를 답니다.

#### 수집기가 남긴 흉터

수집기 자체도 작은 교재입니다. 위키백과가 429를 던지면 Retry-After만큼
물러났다 다시 가고, 네트워크가 끊기면 백오프 재시도하고, 중단되면
받은 만큼 건너뛰고 이어받습니다. 전부 실제 수집 중에 겪고 고친
흉터들입니다.

## 3. 벡터 검색이란 무엇인가

Day 1 3세션에서 `embedding()`을 한 번 호출해 봤고, secretary-agent에서는
기억을 꺼내는 부품으로 썼습니다. 여기서는 그것이 제품의 검색 층이 되니,
색인에서 점수까지 한 번에 정리하고 들어갑니다.

#### 임베딩: 문장을 좌표로 바꾼다

[[embedding|임베딩]] 모델은 텍스트를 받아 길이가 고정된 숫자 배열을
돌려줍니다. 숫자 하나하나에 "칼로리"나 "매운맛" 같은 뜻이 붙어 있는 것은
아닙니다. 중요한 것은 **배치**입니다. 의미가 가까운 문장이 가까운 자리에
놓이도록 학습된 좌표계라서, 글자가 하나도 겹치지 않아도 뜻이 비슷하면
가까이 앉습니다.

Day 1 3세션에서 이미 실측으로 봤습니다.

```text
'국물 요리' vs '탕이나 찌개' = 0.843  (의미가 가깝다)
'국물 요리' vs '주가 상승'   = 0.599  (멀다)
```

"국물"과 "탕"은 글자가 하나도 겹치지 않는데 0.843입니다. `LIKE '%국물%'`은
이 둘을 이어 주지 못합니다. 잠시 뒤 v0.1에서 SQL이 "든든한"에 0건을
내놓는 것과 같은 이야기입니다.

#### 코사인 유사도: 가깝다를 재는 방법

두 벡터가 가까운지는 **사이 각도**로 잽니다. 방향이 같으면 1, 직각이면 0,
정반대면 -1이고, 1에 가까울수록 의미가 비슷합니다. 벡터의 길이는 보지
않습니다. 짧은 단어든 긴 문장이든 가리키는 방향이 같으면 같은 뜻으로
잡으라는 뜻입니다.

Day 1에서는 이 식을 손으로 짜서 확인했지만, 여기서는 컬렉션을 만들 때
거리 함수를 선언하고 Chroma에 맡깁니다.

```python
client.get_or_create_collection(COLLECTION,
                                metadata={"hnsw:space": "cosine"})
```

Chroma가 돌려주는 값은 거리이므로, 화면에 나가는 점수는 `1 - distance`로
뒤집은 코사인 유사도입니다. 곧 볼 v0.1 시연의 `score=0.743`이 바로 이
숫자입니다.

#### 직접 보기: 1000건이 놓인 공간과, 질의가 이웃을 데려오는 순간

말로는 잘 안 잡히는 대목이라 실제 색인을 그대로 그렸습니다. 질의를 하나
고르면 그 문장이 숫자 768개가 되고, 같은 공간에 자리를 잡고, 가까운 것부터
끌려 나옵니다. 점 위에 마우스를 올리면 어떤 음식인지 보입니다.

<VectorSpace />

"든든한 국물 요리"는 국물 무리 한복판에 내려앉습니다. 반면 "100kcal 이하의
저칼로리 음식"은 어느 무리에도 속하지 못하고 가운데 어중간한 자리에
떨어지고, 끌려 나온 것 중에는 100kcal을 넘는 것이 섞입니다. 벡터는 분위기를
알지 숫자를 모른다는 말이 그림에서는 이렇게 보입니다.

#### 색인 시점과 질의 시점

벡터 검색은 두 시점으로 나뉩니다. 미리 한 번 만들어 두는 색인, 그리고
질문이 올 때마다 도는 조회입니다.

```mermaid
flowchart LR
    subgraph IDX["색인 시점 · build_index.py · 한 번"]
        direction TB
        F["음식 1000건<br/>이름 · 분류 · 위키 앞 600자"] --> E1["embedding()"] --> C[("rag · Chroma<br/>벡터 1000개 + food_id")]
    end
    subgraph QRY["질의 시점 · 질문마다"]
        direction TB
        Q["'든든한 국물 요리'"] --> E2["embedding()"] --> K["가장 가까운 top-k"]
    end
    C -.->|"같은 좌표계"| K
```

색인에 넣는 텍스트는 **음식의 서술**입니다. 이름과 분류, 위키 설명이
있으면 앞 600자까지 붙입니다.

```python
text = f"{name} · {category}"
if wiki:
    text += " · " + wiki[:WIKI_CHARS]      # WIKI_CHARS = 600
```

칼로리와 단백질은 일부러 넣지 않았습니다. 수치를 문장으로 적어 벡터에
섞어 봐야 "저칼로리"라는 분위기만 얻고 100kcal이라는 경계는 얻지
못합니다. 숫자는 SQL의 일입니다.

질의 때는 질문을 **같은 모델로** 임베딩해 같은 좌표계에 올린 뒤, 가까운
것부터 k개를 꺼냅니다. 색인과 질의의 모델이 다르면 좌표계가 달라져 거리가
아무 뜻도 갖지 못합니다. 모델 문자열을 `agent/config.py` 한 곳에만 두는
이유입니다.

```python
# 색인·질의 임베딩 — day-01 랩, secretary-agent와 같은 선택
EMBED_MODEL = "gemini/gemini-embedding-001"
EMBED_DIMS = 768     # Day 1에서 본 기본 3072에서 줄여 잡았다
```

#### 벡터가 돌려주는 것은 id와 점수까지다

```python
hits.append({"food_id": meta["food_id"],
             "score": round(1 - res["distances"][0][i], 3)})
foods = {f["food_id"]: f for f in fetch_foods([h["food_id"] for h in hits])}
```

Chroma에서 나오는 것은 `food_id`와 점수뿐이고, 이름도 수치도 pg에서 다시
꺼냅니다. 앞 절의 "원본 한 벌, 색인은 옆에"가 코드에서는 이 대목입니다.
좌표는 의미의 지도이지 값의 장부가 아니라는 것, 이것이 다음 두 층 실습의
전제입니다.

## 7. v0.2 · 깔때기: 싼 층이 줄이고, 비싼 층이 고른다

#### 무엇이 바뀌나

1000건은 컨텍스트에 다 넣을 수 없고, 넣을 수 있어도 비쌉니다. 비용
사다리 순서로 후보를 줄입니다.

```mermaid
flowchart TD
    Q("질문: '다이어트 중 든든한 저녁'") --> P("plan · LLM<br/>조건 분해: 수치 + 의미 질의")
    P --> S1("1차 · PostgreSQL<br/>셀 수 있는 조건 · 공짜")
    S1 -->|"수백 건"| S2("2차 · Chroma<br/>1차 후보 안에서 의미 · 싸다")
    S2 -->|"20건"| S3("3차 · LLM<br/>최종 3건 + 이유 · 비싸다")
```

여기서 [[langgraph|LangGraph]] 그래프가 처음 등장하는데, **checkpointer가
없습니다**. 추천은 질문 하나로 끝나는 파이프라인이라 thread에 걸칠
상태가 없습니다. 모든 그래프에 기억이 필요한 것은 아닙니다.

#### 코드 발췌: plan이 질문을 두 갈래로 가른다

```python
def plan(state: FunnelState) -> dict:
    """질문을 셀 수 있는 조건(SQL)과 흐릿한 조건(벡터)으로 분해한다."""
    response = completion(model=pick_model(), messages=[...], response_format={"type": "json_object"})
    # {"max_kcal": 200, "min_protein_g": null,
    #  "exclude_categories": ["음료 및 차류"], "semantic_query": "든든한 국물 요리"}
```

#### 실행 결과: 깔때기가 좁아지는 것을 숫자로

```text
[질문] 다이어트 중인데 저녁으로 든든한 국물 요리 뭐 없을까?
  plan이 분해한 조건: {"max_kcal": 200, "exclude_categories": ["음료 및 차류", "빵 및 과자류"], …}
  깔때기: 전체 1000 → sql 500 → vector 20 → select 3

  ✔ 닭곰탕 (국 및 탕류 · 51.0kcal · 단백질 7.5g)
    칼로리가 낮으면서도 단백질 함량이 높아 다이어트 중에도 든든하게 즐기기 좋습니다.
  …

[질문] 운동 끝나고 단백질 보충되는 담백한 음식 추천해줘
  plan이 분해한 조건: {"min_protein_g": 15, …}
  깔때기: 전체 1000 → sql 99 → vector 20 → select 3

  ✔ 닭꼬치구이 (구이류 · 181.0kcal · 단백질 32.1g)
  …
```

#### 결과 읽기

질문에 따라 깔때기의 모양이 달라집니다. 다이어트 질문은 칼로리 조건으로
500까지, 단백질 질문은 min_protein 15로 **99까지** 줄인 뒤에야 벡터와
LLM이 일합니다. LLM 앞에 놓이는 것은 언제나 20건뿐입니다. 이것이 이
제품의 비용 구조입니다.

       ③ 조건: 원본 수치가 사용자 조건을 정말 충족하는가"""

불합격은 사유와 함께 select로 돌아가 **한 번** 재선별되고, 통과분의

[[reflexion|Reflexion]] 순환(생성 → 평가 → 재시도)이 제품이 된 모습이고,
평가자가 LLM이 아니라 코드라는 점이 다릅니다. "LLM 출력을 그대로 믿지
않는다"가 이 에이전트의 핵심 규율입니다.

## 이 세션이 남기는 것, 그리고 Day 2의 끝

- 검색 층은 대체가 아니라 분담이다. SQL은 숫자를, 벡터는 의미를,
  LLM만 이유를 안다
- 깔때기는 비용 사다리다. 싼 층이 줄여준 뒤에만 비싼 층이 일한다
- LLM 출력은 그럴듯함이지 보증이 아니다. 내보내기 전에 코드가 원본과
  대조한다
- 근거는 응답의 일부다. 수치는 원본으로, 설명은 출처 링크와 함께
- 원본 한 벌, 색인은 옆에. 색인은 파생물이라 언제든 다시 만든다

Day 2가 여기서 닫힙니다. diet-agent가 그래프를, booking-agent가

**여럿**이 협업하는 순간 무엇이 필요해지는가, 그것이 Day 3의 주제입니다.
