
손님과 사장은 서로 다른 주소에서 각자 로그인하는,
**완전히 다른 화면**을 씁니다.

<Slide>

### 두 가지가 처음입니다

- **`app` 안에 그래프가 둘입니다.**
  - 쓰기 앞에 멈추는 손님 예약 그래프
  - 조회 전용인 사장 어시스턴트 그래프
  - 하나의 LangGraph 앱이 그래프 하나라는 법은 없습니다.
- **`db`는 이번에 일이 두 배입니다.**
  - 예약 도메인 데이터에 더해, **대화 상태(checkpoint)까지** 이 안에 삽니다.
  - diet-agent가 남긴 결핍이 여기서 풀립니다.

</Slide>

<Slide>

### 그래프가 둘인 이유

- **손님 예약 그래프**: 쓰기 앞에서 멈춥니다. 되돌릴 수 없는 행위를 다룹니다.
- **사장 어시스턴트 그래프**: 조회 전용입니다. 멈출 일이 없습니다.

같은 앱 안에서도 **위험도가 다르면 그래프를 따로 둡니다.**

</Slide>

### 이름이 같은 두 승인을 미리 갈라 둡니다

| | 손님의 확인 (v0.3) | 사장의 승인 (v1.0) |
| --- | --- | --- |
| 정체 | 그래프의 interrupt | 도메인 상태 머신 |

## Part 2. 출발점

diet-agent의 도착점이 이 저장소의 출발점입니다.

</Slide>

<Slide>

### 앞 세션이 한 시간에 걸쳐 세운 것이 v0.1에 이미 있습니다

- advisor ↔ tools 순환
- conditional edge
- reducer
- checkpointer

**새로 배우는 것은 그래프 모양이 아닙니다.**

</Slide>

<Slide>

### 세 가지 질문

- 그 상태는 **어디에** 사는가 (v0.1 → v0.2)
- 되돌릴 수 없는 행위 앞에서 **누가 확인하는가** (v0.3)
- 지나간 상태로 **되돌아갈 수 있는가** (v1.0)

</Slide>

<Slide>

### 코드 발췌: 신원은 LLM의 인자가 아니다

```python
class BookingState(TypedDict):
    """messages에는 reducer가 붙고(델타 반환), 신원 두 칸은 매 호출 덮어쓴다."""
    messages: Annotated[list[dict], operator.add]
    customer_id: int
    customer_name: str

def tools(state: BookingState) -> dict:
    """요청된 도구를 전부 실행한다. customer_id는 상태에서 주입 — LLM 인자가 아니다."""
    ...
    run_tool(call["function"]["name"], call["function"]["arguments"],
             customer_id=state["customer_id"])
```

</Slide>

<Slide class="center">

### "저 3번 손님인데요"에 속지 않습니다

customer_id는 로그인에서 와서 그래프 상태에 실리고,
tools 노드가 **실행 시점에 주입**합니다.

남의 이름으로 예약하는 길을 **스키마 수준에서** 막습니다.  
LLM은 신원 인자를 만들 수조차 없습니다.

</Slide>

<Slide>

### 릴리즈 사다리: 상태의 거처가 자라는 순서

| 릴리즈 | 상태 | 테스트 |
| --- | --- | --- |
| v0.1 | 손님 예약 대화 동작. 기억은 프로세스 메모리 (재시작 = 백지) | 10개 |
| v0.2 | PostgreSQL checkpointer. 재시작 생존, 상태는 SQL로 읽는 행 | 12개 |
| v0.3 | 쓰기 직전 interrupt. 확인 카드와 승인/보류 분기 | 16개 |
| v1.0 | 사장 입장 완성 + 조회·취소 + time-travel | 27개 |

### 코드 발췌: 로그인은 인증이 아니라 식별

```python
def normalize_phone(raw: str) -> str:
    """숫자만 남긴다 — 010-1111-2222와 01011112222는 같은 손님이다."""
    return re.sub(r"\D", "", raw)

@app.post("/login")
def login(body: LoginBody):
    """이름+전화로 손님을 찾거나 만든다. 같은 전화는 언제나 같은 손님이다."""
    row = conn.execute(
        """INSERT INTO customers (name, phone) VALUES (%s, %s)
           ON CONFLICT (phone) DO UPDATE SET name = EXCLUDED.name
           RETURNING id, name""", (body.name, normalize_phone(body.phone))).fetchone()
    ...
    return {"customer_id": customer_id, "name": name, "thread_id": f"cust-{customer_id}"}
```

</Slide>

<Slide>

### 전화번호가 곧 손님입니다

- 대화 thread도 손님마다 하나(`cust-<id>`)입니다.
- 식별자는 저장 전에 **정규화**합니다.
  하이픈을 넣든 말든 같은 손님이어야 하기 때문입니다.
- 같은 손님이 다시 로그인하면 같은 대화가 이어집니다.
- 비밀번호도 토큰도 없는 **수업용 최소 구성**이라는 것은 밝혀 둡니다.

</Slide>

<Slide>

### 사고 재현: 재시작 한 방이면 전부 잊는다
::sub[v0.1의 checkpointer는 MemorySaver, 즉 app 서버 프로세스의 메모리입니다]

```bash
docker compose exec app python demos/amnesia.py          # 1부: 두 턴 대화
docker compose exec app python demos/amnesia.py --probe  # 기억 확인
docker compose restart app
docker compose exec app python demos/amnesia.py --probe  # 재시작 후 다시
```

시연 스크립트가 그래프를 직접 import하지 않고 서버의 `/chat` API로 말을 거는
이유가 있습니다.  
**재시작으로 사라지는 것이 바로 그 프로세스**이기 때문입니다.

</Slide>

<Slide>

### 재시작 전: 다른 프로세스에서 물어도 기억한다

```text
=== 기억 확인: 같은 thread에 이어 묻는다 ===

[손님] 방금 제가 몇 명이라고 했죠?
[상담사] 김서연 님, 6명이라고 말씀하셨습니다!
6분이서 여유롭게 이용하시기에는 룸1(6인석)이나 룸2(10인석) 모두 좋습니다. …
```

기억의 주인이 **서버 프로세스**라는 뜻입니다.

</Slide>

<Slide>

### 재시작 후: 같은 thread, 같은 질문

```text
=== 기억 확인: 같은 thread에 이어 묻는다 ===

[손님] 방금 제가 몇 명이라고 했죠?
[상담사] 김서연 님, 방금 저에게 인원수를 따로 말씀해 주지 않으셨어요!
예약하시려면 **날짜, 시간, 그리고 인원수**를 알려주세요. …
```

</Slide>

<Slide>

### 결과 읽기: 열쇠는 있는데 금고가 사라졌다

- 같은 thread_id인데 답이 갈렸습니다.
- thread_id는 **열쇠일 뿐**이고,
  금고(MemorySaver의 딕셔너리)가 프로세스와 함께 사라졌습니다.

</Slide>

## Part 4. v0.2 · 이사

상태의 거처가 PostgreSQL로

### 그래프 모양은 한 글자도 안 바뀝니다

```python
# v0.2: 상태의 거처가 pg로 옮겨진다. 이 세 줄이 재시작 생존의 전부다.
pool = ConnectionPool(DATABASE_URL, kwargs={"autocommit": True})
checkpointer = PostgresSaver(pool)
checkpointer.setup()   # checkpoint 테이블이 없으면 만든다 (멱등)

graph = builder.compile(checkpointer=checkpointer)
```

`git diff v0.1 v0.2 -- app/agent/graph.py`의 핵심이 이것입니다.  
**compile에 꽂는 부품만 바뀝니다.**

</Slide>

### 기억의 거처가 옮겨간다

- 실행

기억이 "어딘가에 저장된다"가 아니라 **SQL로 읽을 수 있는 행**입니다.

</Slide>

### 그래프의 눈으로 복원한 같은 데이터

```text

  [assistant] (도구 호출)
  [tool] {"res_date": "2026-08-21", "res_time": "18:00", "party_size"…
  [assistant] 김서연 님, 다음 주 금요일(8월 21일) 저녁 18:00에 6분 예약 가능한 룸은 …
```

</Slide>

<Slide>

### 결과 읽기: 노드 단위로 쌓인다

- `setup()` 한 번이 만든 테이블 4개에 thread별 checkpoint가 쌓입니다.
- **턴마다 하나가 아니라 노드 단위로** 쌓입니다.
  두 턴 대화에 13개
- 이 촘촘함이 **v1.0 time-travel의 재료**가 됩니다.

</Slide>

<Slide>

### 왜 노드 단위로 쌓는가

- 턴 단위로만 쌓으면 "그 턴의 중간"으로는 돌아갈 수 없습니다.
- 노드 단위면 **confirm 직전** 같은 지점을 정확히 집을 수 있습니다.
- v1.0의 time-travel이 이 촘촘함 위에서 돕니다.

</Slide>

```mermaid
sequenceDiagram

    U->>UI: "창가 자리로 예약해 주세요"
    UI->>APP: POST /chat

    APP-->>UI: answer 대신 interrupt 페이로드
    UI-->>U: 확인 카드 (버튼 2개)
    U->>UI: ✅ 진행
    UI->>APP: POST /confirm (Command resume)
    Note over APP: 멈춘 자리에서 재개<br/>→ tools가 그제야 db에 쓴다
    APP-->>UI: answer ("접수되었습니다")
```

### 코드 발췌: confirm 노드

```python
WRITE_TOOLS = {"request_reservation"}   # 되돌릴 수 없는 도구 — 사람 확인을 거친다

def confirm(state: BookingState) -> dict:
    """쓰기 도구 앞의 관문: interrupt로 멈춰 손님의 최종 확인을 받는다."""
    last = state["messages"][-1]
    write_calls = [c for c in last["tool_calls"] if c["function"]["name"] in WRITE_TOOLS]
    decision = interrupt({          # ← 여기서 실행이 멈춘다
        "type": "confirm_reservation",
        "requests": [json.loads(c["function"]["arguments"] or "{}") for c in write_calls],
    })
    if decision.get("approved"):
        return {"messages": []}     # 빈 델타 — 도구 실행(tools)으로 그대로 진행
    # 보류: 도구를 실행하지 않되, 모든 tool_call에 회신은 해야 대화가 성립한다
    return {"messages": [ ...거절 회신 tool 메시지들... ]}
```

</Slide>

<Slide>

### interrupt()가 하는 일

- 페이로드를 **호출자에게 올려보내고 그 자리에서 멈춥니다**.
- `Command(resume=결정)`가 돌아오면 **같은 줄에서 반환값으로** 이어집니다.
- 읽기 도구(`check_availability`)는 이 관문을 거치지 않습니다.

**사람을 세우는 것은 되돌릴 수 없는 행위 앞에서만입니다.**

</Slide>

### 코드 발췌: 세 겹 방어

```python
def run_sql(args: RunSqlArgs) -> dict:
    query = args.query.strip().rstrip(";").strip()
    if not query.lower().startswith("select"):
        return {"error": "SELECT로 시작하는 조회만 허용된다. …"}     # 1겹
    if ";" in query:
        return {"error": "한 문장만 허용된다."}                      # 1겹
    if " limit " not in query.lower():
        query += " LIMIT 50"                                        # 2겹
    with psycopg.connect(DATABASE_URL) as conn:
        conn.execute("SET TRANSACTION READ ONLY")   # 3겹: pg가 쓰기를 거부
        cur = conn.execute(query)
```

</Slide>

<Slide>

### 방어를 직접 두드린 실측

```text
[쓰기 시도] DELETE FROM reservations
  → SELECT로 시작하는 조회만 허용된다. 쓰기·DDL은 이 도구의 일이 아니다.

[다중 문장] SELECT 1; DELETE FROM reservations
  → 한 문장만 허용된다.

[SELECT 위장 쓰기] SELECT setval('reservations_id_seq', 999999)
  → 쿼리 실패: cannot execute setval() in a read-only transaction
```

</Slide>

<Slide class="center">

### 세 번째 줄이 핵심입니다

`setval()`은 SELECT로 시작하지만 시퀀스를 바꾸는 **진짜 쓰기**라
문자열 검사문을 통과합니다.

그것을 pg의 READ ONLY 트랜잭션이 잡습니다.  
**문자열 검사는 뚫려도 마지막 방어선이 남아 있어야 합니다.**

## 이 세션이 남기는 것

- 상태의 거처가 제품을 가른다.
  MemorySaver는 프로세스, PostgresSaver는 db의 행이고, 바꾸는 데 세 줄이면 된다.
- interrupt는 되돌릴 수 없는 행위 앞의 관문이다.
  멈춘 상태도 checkpoint라서, 영속성이 있어야 비로소 웹 제품이 된다.
- 승인이라고 다 같은 승인이 아니다.
  손님 확인은 그래프의 멈춤, 사장 승인은 도메인 상태 머신이다.
- LLM에게 SQL을 맡기려면 방어를 겹으로 두른다.
- checkpoint 목록은 시간축이다. 과거에서 다시 실행하면 평행 계보가 열린다.
